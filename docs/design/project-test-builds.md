# Web previews and desktop test builds

Administrator-uploaded delivery packages declare a `delivery_target`. Existing packages default to `web` and retain the current allocated-port preview flow. A desktop package declares a build directory, Linux shell command, exact output filename and timeout (30–1800 seconds). Configuration is immutable with the package; ordinary users cannot change the server-side command, target repository or another member's branch through the build API. A new package supplies a revised build contract.

Desktop flow: develop → commit/push the personal Gitea branch → **生成测试版** in project collaboration / **测试版本** → download → local test → develop again. Building does not require merging main; the existing reviewed PR flow remains the way to combine accepted changes. Each click records a new build against the exact SHA resolved by the server from the authenticated member's branch. It never builds an unrelated uncommitted directory or follows a branch that moved after submission.

The queue, immutable build contract, status, logs and artifact checksum are stored in PostgreSQL. One queued/running build per member/project prevents duplicate clicks. Agentd claims only its owner's jobs when its AI runs are idle. It obtains a bounded, validated source snapshot through the portal and runs the configured command as worker UID 1002 in a new temporary directory. Existing container isolation/resource limits apply; no Docker socket, production publisher or platform credential enters the build subprocess. Heartbeats renew a short lease; interrupted work becomes failed, and a retry is a new build record. AI work and current project files are not used as the build directory.

Only exit zero plus an actual regular output file (maximum 512 MiB) allows success. The bridge opens every artifact path component with `O_NOFOLLOW` and pinned directory descriptors; it rejects symlinks, hardlinks and directories. The portal stores the result under its persistent artifacts volume with SHA-256. Download requires an active project membership or administrator permission on every request. Artifact names, logs and statuses are untrusted display data and are never interpreted as HTML or executable server instructions.

Removing a member revokes downloads and prevents new jobs; removing a project prevents its members from using builds. Existing Git repositories, commits, PRs, LiteLLM accounting and build records/artifacts are retained. Archived project artifacts remain administrator-accessible. Builds do not push source, update a production installer feed, deploy a website, or count as local business acceptance.

## Runtime scope

The first executor is the existing Linux FDE container. It supports toolchains already installed there and projects that can cross-compile on Linux. An Electron Windows portable ZIP can be built with electron-builder's Windows directory target and executable resource editing disabled, then zipped. Windows-only native toolchains, MSI custom actions, signing and macOS packaging require an isolated executor for that OS; a Linux job must fail explicitly rather than manufacture a successful artifact.

SDADS_Kit is a private delivery-package example, not platform source. Its existing `deploy-desktop.yaml` publishes the production update feed and must not be copied as the test pipeline. A test packaging recipe must use a distinct application identity/profile and disable production auto-updates in application code; `--publish never` only disables upload and is not a runtime updater switch. Import only the intended project snapshot into its private Gitea delivery repository; never add the application's business code or credentials to the public FDE Station fork.
